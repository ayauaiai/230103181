## 1. Introduction

This laboratory evaluates the performance of parallel Python workloads
on an AMD Ryzen 5 5600H processor. The experiments cover timer
calibration, false sharing, strong and weak scaling, empirical roofline
analysis, cache-blocked matrix multiplication, and scheduling strategies
for skewed workloads.

The experiments use Python multiprocessing to distribute computational
work across processes. Performance is evaluated using median execution
time, speedup, parallel efficiency, load imbalance, throughput, and
verification hashes.

The Ryzen 5 5600H uses six homogeneous Zen 3 CPU cores with simultaneous
multithreading (SMT). It does not use a hybrid P-core/E-core design.
Therefore, the performance change observed when increasing the process
count from six to seven is interpreted as crossing the physical-core
count and beginning to share physical cores through SMT, rather than as
crossing a P-core/E-core boundary.

The L1 data-cache and cache-line figures above are architecture-based
expectations. The Windows cache query returned an L1 installed-size
value of 384 KB, but this value does not independently identify the L1
data cache alone. The cache-line size was not confirmed by the Windows
query.

### Discussion

variability may also affect the results.

## 7. Phase 4 --- Skewed Workloads and Dynamic Scheduling

### Objective

Compare three scheduling approaches for a skewed workload of 8,000 items
across six physical workers:

1.  Contiguous block static scheduling.
2.  Cyclic round-robin static scheduling.
3.  Dynamic scheduling using a shared synchronized queue.

The per-item workload increases with the item index according to:

\[
K(i)=1+`\left`{=tex}`\lfloor`{=tex}`\left`{=tex}(`\frac{i}{40}`{=tex}`\right`{=tex})\^2`\right`{=tex}`\rfloor`{=tex}
\]

Dynamic scheduling was tested with chunk sizes 1, 8, 64, and 512. Each
strategy was run three times. The reported wall time is the median of
the three runs. Worker-time telemetry and load imbalance were taken from
the run whose wall time was closest to that median.

The load imbalance factor is:

\[ `\lambda `{=tex}= `\frac{\max(t_{\text{worker}})}`{=tex}
{`\operatorname{average}`{=tex}(t\_{`\text{worker}`{=tex}})} \]

A value closer to 1 indicates more balanced worker execution times.

### Discussion

Contiguous block scheduling performed worst, with a median wall time of
12,952.293 ms and a load imbalance factor of 2.4938. This occurs because
the workload grows with the item index: later contiguous blocks contain
much more computational work than earlier blocks.

Cyclic scheduling distributed low- and high-cost indices across workers
more evenly. Its median wall time decreased to 6,909.106 ms, and its
load imbalance factor improved to 1.1022.

Dynamic scheduling with chunk size 1 achieved the best measured result:
5,489.620 ms and λ = 1.0027. It provided the most balanced worker times
and the lowest wall time among the tested strategies. In this
experiment, the improved balance outweighed the synchronization cost of
frequently acquiring the shared queue lock.

As chunk size increased, the number of queue operations decreased, but
work distribution became less flexible. At C = 512, the load imbalance
factor rose to 1.3521 and the median wall time increased to 8,157.777
ms. This illustrates the trade-off between queue synchronization
overhead and the ability to distribute a highly skewed workload
dynamically.

## 8. Overall Conclusions

The experiments demonstrate that multiprocessing performance depends not
only on the number of processes but also on memory behavior, workload
structure, scheduling, and synchronization overhead.

The main findings are:

1.  **Calibration:** The average `perf_counter_ns()` call latency was
    95.47 ns.
2.  **False sharing:** The stride sweep did not show a strong,
    consistent false-sharing effect. Increasing process count improved
    throughput, but efficiency declined.
3.  **Strong scaling:** The workload achieved a speedup of 5.874 at 12
    processes, with efficiency of 0.489. The strongest scaling region
    was up to approximately six physical cores.
4.  **Weak scaling:** Efficiency declined from 1.000 at one process to
    0.428 at 12 processes, with irregular timing across process counts.
5.  **GEMM optimization:** The cache-blocked matrix multiplication with
    BS = 128 achieved the best measured GEMM performance, 0.04808
    GFLOP/s, and passed the numerical comparison. The Phase 3
    compute-ceiling measurement requires correction because its checksum
    overflowed to infinity.
6.  **Scheduling:** Dynamic scheduling with C = 1 was the best of the
    tested Phase 4 configurations, with median wall time 5,489.620 ms
    and λ = 1.0027.

Overall, the results show that balancing work across processes is
especially important for skewed workloads. Static contiguous
partitioning is unsuitable when task cost grows with the task index.
Cyclic scheduling improves balance, while a fine-grained dynamic queue
provides the best result for this particular workload and machine.

## 10. Limitations

-   The measurements were collected on one Windows laptop and may vary
    with background processes, power mode, CPU temperature, and
    operating-system scheduling.
-   The Phase 1 stride results have substantial variability and do not
    conclusively isolate false sharing from other multiprocessing
    effects.
-   Weak-scaling wall times were irregular, so the results should not be
    interpreted as ideal weak scaling.
-   The Phase 3 compute benchmark returned an infinite checksum. Its
    reported compute ceiling and ridge point are therefore not reliable
    and require a corrected benchmark rerun.
-   The Phase 3 shared-memory cleanup emitted `BufferError` warnings
    because buffer views remained exported during close.
-   Phase 4 used three runs per strategy. More repetitions would improve
    confidence in the medians, especially where run-to-run variation is
    high.
